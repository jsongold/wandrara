Web に出すデータモデル（提案）

core_type ごとに出力の形を決める。形の正本は main にマージされたコード。DB の表は正規化したまま、画面は出力の形だけを読む。下の見本は wr-ito-033（ポッケまほろ伊豆）の投入の原本から作った。

1. 全体の形

DB の表accommodations と詳細の表（正規化）
→
組み立てtoAccommodationView(rows)
→
出力の形AccommodationView（zod で確かめる）
→
Web詳細 /d/[slug]・admin・カード
  • 出力の形は core_type ごとに 1 つ（AccommodationView …）。kind では出し分けない。共通の部分は DestCommon に置く
  • 画面は出力の形だけを読み、DB の表の形を知らない。表を直しても、組み立てを直せば画面は変わらない
  • version の欄は持たない。main の最新が正。形を変えるときは、組み立て・型・画面を同じ PR で直す
  • 語彙（設備・風呂・注意点の種類）は出力の時点でラベルに変える。画面に open_air などの値が出ない
  • 似ているジャンルはまとめる。サウナは風呂の種類の 1 つにする（表も型も分けない）

2. 型は core_type ごとに 1 つ

出力の型は 2 段。DestCommon（全コア共通）→ AccommodationView（core_type ごと）。kind では出し分けない。kind はバッジに出すだけで、画面はどの kind でも同じ並びで出し、データの無いトピックは出さない。

画面の見出しは、トピックごとに独立させる。チェックイン・アウトは宿に必須で、どの宿でも必ず出す。見出しにせず、紹介文のすぐ下に時刻だけを並べる。そのあとの並びは 料金 → 部屋 → 食事 → 風呂 → 設備 → ペット → 条件 → 駐車場 → アクセス → 周辺 → 注意点 → 予約。設備と条件だけは、小さな項目をまとめる見出しにする。

2.5 料金は言葉を使わず型に収める

料金と料金区分には、文（note・name・rule の文字列）の列を持たせない。「どの日に・何人で・何に・いくら」をすべて型で持つので、日付と人数を入れれば合計を計算でき、カレンダーにも出せる。画面の言葉（「土曜と指定日」など）は型から作る。

type SeasonRule = {
  validFrom: string; validTo: string  // この料金表の期間（YYYY-MM-DD）
  isDefault: boolean   // どの区分にも当てはまらない日（「②③④以外」）
  priority: number     // 重なったら大きい方が勝つ（「③④以外」）
  weekdays?: (1|2|3|4|5|6|7)[]        // 1=月 … 7=日（体験の weekdays と同じ）
  holidays?: boolean                  // 祝日
  dayBeforeHoliday?: boolean          // 祝前日
  dates?: { from: string; to: string }[]  // 当てはまる日（年つき）
}

type Price = {
  kind: "room" | "service_fee" | "bath_tax" | "lodging_tax" | "cleaning"
  per: "house_night" | "person_night" | "stay"
  amount: number; amountMax?: number; currency: string
  taxIncluded?: boolean
  guestsMin?: number; guestsMax?: number   // room の人数の幅
  audience?: "adult" | "child" | "all"
  ageMin?: number; ageMax?: number         // 子ども料金の年齢
  meals?: "none" | "breakfast" | "dinner" | "both"
  season?: string      // 区分の key。空なら全部の日
}
// 日付から区分を決める（言葉を読まずに決まる）
function seasonFor(date, seasons) {
  const hits = seasons.filter(s => !s.isDefault
    && inRange(date, s.validFrom, s.validTo)
    && (s.weekdays?.includes(isoWeekday(date))
     || s.dates?.some(d => inRange(date, d.from, d.to))
     || (s.holidays && isHoliday(date))
     || (s.dayBeforeHoliday && isHoliday(next(date)))))
  return maxBy(hits, "priority") ?? seasons.find(s => s.isDefault)
}

3. 画面

画面は web-output-model.html にある（一棟貸し wr-ito-033・ホテルと旅館の架空の見本）。

画面で変わること

  • デザイン（バッジ・タイトル・紹介文・行・アクセス）は今のまま。行の並べ方と中身だけを変える
  • 「未検証」のラベルは画面に出さない（確認の状態はデータには残す）
  • 詳細のある行（›）をタップすると、その行のすぐ下に詳細が開く（ページやシートは出さない）
  • トピックはそれぞれ独立した見出しにし、チェックイン・アウトは必須で、紹介文のすぐ下に時刻だけを必ず出す（wr-ito-033 は元データに無いので、見本では --:--。本来は upload の validation で落ちる）。そのあと 料金 → 部屋 → 食事 … の順に出す。ペットも独立。設備と条件だけは、小さな項目をまとめる見出し
  • 設備は中カテゴリ（風呂・キッチン・屋外・通信・駐車場 …）を行の名前にし、小カテゴリ（個々の設備）を値に並べる
  • 同じ種類の行は 1 行にまとめる（風呂 1〜3 → 風呂）。値はラベルで出す（open_air → 露天風呂）
  • 料金は部屋ごとに 1 行の表（部屋・人数・最小・最大・備考）。行を開くと区分ごとの最小〜最大と追加の料金。区分 × 人数の表をそのままは出さず、公式サイトへのリンクを残す。注意点の 19 行（同じ文の繰り返し）は出さない
  • 持っている情報は全部、行か行の下の詳細で見られる。最後に出典を出す
  • DB には料金を全部、型で持つ（2.5）。画面の表はそこから作る
  • kind では出し分けない。どの kind も同じトピックの並びで、データの無いトピックは出さない
  • 紹介文は公式の文の丸写しではなく、短く書き直したものを出す想定

  • 小カテゴリの code は、1 つの中カテゴリにだけ属する
  • 一覧はコードに 1 つだけ置き、DB の check・bundle の zod・出力のラベルが同じ一覧を見る
  • accommodation_amenities.kind は小カテゴリの code。options（text[]、一覧で決めた値だけ）と count（数）を足す
  • 一覧に無い code は upload で受け付けない。足りなければ一覧を直す PR を出す
  • 中カテゴリの並び順は一覧の順。画面もその順に出す
  • Wi-Fi の速さ・測った日・机は accommodation_internet に残す（詳しいほど良い）。画面では通信の Wi-Fi の行の下に開く
