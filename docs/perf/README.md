- 書き足し方：各 MS の PR で「5. 決定と根拠」と「6. 結果」に追記する。1〜4 は事実が変わったときだけ直す。

## 1. 現状分析

2026-11-19 時点。コードを読んだ調査（本番の計測なし）。数値の「推測」は MS0 の計測で確定する。

- 構成：Next.js 16（App Router）+ Supabase。Vercel の関数は `hnd1`（東京）の 1 リージョン。Supabase のリージョンは未確認。
- トップ（`/ja`）は `searchParams` を読むため毎リクエスト動的。フィードは全件を RSC で送り、描画は 6 枚ずつ。
- 画像は `next/image` 経由。`deviceSizes: [1080]` の 1 種類（`imageSizes` は既に `[256, 640]` があり、1080 のみなのはカルーセル）、形式は WebP のみ、`minimumCacheTTL` 31 日。Vercel Hobby の変換枠（月 5K）を意識した設計。
- 先読み：カード 1 枚で詳細最大 7 件（本体 1 + 関連タイル 6）を `prefetch={true}`。保存一覧は全件。
- 認証：proxy が静的ファイル以外の全リクエストで `auth.getUser()` を呼ぶが、未ログインではセッションが無く SDK が `/user` の通信前に戻るため、認証の通信は起きない。クライアントは Supabase を初期 JS に含み、表示直後に `getUser()`（未ログインでも通信は無し）。
- サーバーキャッシュ：`getCatalog` は `use cache` + `cacheLife("minutes")`。インスタンス間で共有されない。
- 良い点：maplibre と地図データは動的 import。`content-visibility: auto`。写真の描画枚数制限。
- 環境への適応：Save-Data・回線品質の判定、service worker、`error.tsx` はいずれも無い。

## 3. 問題の一般化

個別の問題は、次の 6 つの型にまとまる。今後の機能でも同じ型を作らないための判断の軸にする。

1. **必要になる前に送る**（P1・P3・P4・P7・P8・P9）：見えていない・使わないものを先に送っている。原則「表示に必要な分だけ、必要になったときに送る」。
2. **一律に送る**（P4・P9・P10）：回線・端末・通信量の設定を見ずに同じものを送る。原則「利用者の環境で送る量と方法を変える」。
3. **同じ仕事を繰り返す**（P2・P5・P6）：結果を再利用せず、毎回計算・往復する。原則「1 回で済むものは 1 回にし、キャッシュが効く形にする」。
4. **失敗と上限を想定していない**（P10・P11）：失敗や件数上限で黙って壊れる。原則「失敗しても部分的に使え、上限は明示的に扱う」。
5. **件数に比例して計算量・メモリが増える**（P2・P12）：データが増えるほど処理が重くなる。原則「件数が増えても処理が比例して増えない形にする（共有・分割・必要な分だけ読む）」。
6. **往復の待ち合わせが表示を待たせる**（P5・P7・P12）：複数の取得や初期化の完了を待ってから表示している。原則「表示に必要なものだけを待ち、残りは並行・後回しにする」。

判断は、通信量と表示速度に加えて、操作の待ち時間・SEO・データの鮮度・画像変換の費用も天秤にかける。
